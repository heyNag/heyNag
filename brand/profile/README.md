# GitHub and heyNag.com

This directory records the personal profile settings and the connection to the future website. The GitHub profile is the introduction. The website will give Nag's work more room for stories, demonstrations and the moth's expressive motion.

| File | Purpose |
| --- | --- |
| `profile.json` | Proposed account name, bio, avatar, public pins and repository descriptions; publication status is explicit |
| `publication.json` | Separately verified application receipts, so a Git commit is not confused with saved account settings |
| `public-evidence.json` | Verified public source references and limits behind the three project blurbs |
| `continuity.json` | Shared identity and behavior across GitHub and the future website |
| `../../README.md` | GitHub's profile README |
| `../source/applications-v5.json` | Current header and avatar exports, source and reproducible recipe |
| `../reviews/2026-11-07-github/` | This profile application's evidence and specialist review |

Keep the GitHub introduction and website stories in Nag's voice. The moth is the recurring companion; Nag remains the maker. The profile's three public projects are a sample, not a claim to represent all private work. A future private-project case study needs a separate decision about what may be shared.

The intended website repository is `heyNag/heynag.com`, created when website development starts. It should consume a versioned copy of the shared assets, with the source commit and manifest recorded. It must not develop a separate moth or quietly change its proportions. GitHub keeps native text and static artwork; the website can use the existing character rig and intentional motion with an equivalent quiet path.

To update the profile:

1. Edit the root README and applicable values in `profile.json`.
2. Verify public project claims and destinations. Leave the website URL empty until the site has a useful live destination.
3. Re-export artwork only when the character application changes. Preserve the tiny geometry and paired light/dark treatment.
4. Render the README with GitHub's Markdown renderer and inspect it in GitHub's layout at desktop and narrow phone widths, including both themes. Account-preview screenshots must clearly state when settings have not been saved.
5. Follow the standing-team review in `AGENTS.md`. Keep scoped scores, evidence and unresolved objections.
6. Publish within the user's authorization, then verify the live README, account settings, avatar and selected pins. Update publication status only for changes actually observed live.

Profile account settings and pinned repositories are separate from a Git commit. A successful push alone does not mean the avatar, bio or pins have changed. GitHub has one account avatar; use the universal day avatar on its paper ground. The README's paired headers follow the viewer's color-scheme preference.

GitHub's native interface controls typography, link colors, layout and accessibility behavior. Reuse the identity across platforms without trying to reproduce the whole website inside a README.
